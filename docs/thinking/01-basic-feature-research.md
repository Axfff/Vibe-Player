## 1. 建议先讨论什么

若兼顾课程提交与之后的 AI 扩展，最优先讨论：

1. **自定义多歌单**：让用户长期保存不同用途的音乐集合。
2. **手动场景标签 + 标签筛选**：让“学习、跑步、夜晚”等个人语义成为可操作的数据。
3. **最近播放 / 轻量历史**：找回听过的曲目，之后再决定是否增加有效播放次数。

**跨字段搜索**适合作为最小的入门任务：范围较小，能先跑通一次需求、分支、实现、审阅和验收流程。但它单独作为整个项目的主要亮点偏轻。

初始调研建议可从一个主功能及可选配套功能考虑。这份候选表不要求一次实现所有项目。当前已经收敛为先讨论自定义多歌单；其他基础功能与 AI 方向留到后续。

## 2. 当前 APP 的基础

仓库名为 Vibe-Player，但 README 和代码仍以 **Music Player GO** 为基础，版本配置为 4.4.24。它是读取本机音乐库的原生 Android 播放器。[R1]、[R2]

| 层次 | 当前实现 | 对新增功能的含义 |
| --- | --- | --- |
| UI | Kotlin、XML、ViewBinding、Fragment、RecyclerView、ViewPager2 | 优先延用现有 UI 结构即可 |
| 本地曲库 | MediaStore 查询，载入内存后分组、排序与过滤 | 可直接利用已有歌名、艺人、专辑、时长、年份等字段 |
| 播放 | Android MediaPlayer、自有 PlayerService、MediaSessionCompat | 歌单与搜索通常可复用播放入口；不必重写播放器 |
| 本地保存 | SharedPreferences + Moshi JSON | 小数据可以包装现有方式；增长型历史与关联数据再考虑独立数据库 |
| 网络 | 当前 Manifest 无 INTERNET 权限，FAQ 说明只播放本地曲库 | 在线 AI 会引入新的联网与服务依赖，届时另行设计 |
| 构建 | Kotlin 1.8.21、AGP 8.0.2、Java 17、min SDK 21、compile/target SDK 33 | 此处是基线事实；本次不提出全项目升级 |
| 工程验证 | 已有 Android CI 构建/上传 APK 配置；完整目录中未见测试源码 | 后续应验证实际构建，并为选定功能加入有价值的验收与测试 |

架构证据：[R2]、[R3]、[R4]、[R5]、[R6]。存在 CI 配置不等于已确认它在当前环境运行成功。

## 5. 重点候选的需求、验收与风险

### B1. 自定义多歌单

**用户问题：** 一个收藏列表无法方便地保存“通勤、专注、跑步”等多个用途的集合；当前队列也不提供多个长期命名集合。

**最小范围：**

- 创建、重命名、删除歌单。
- 从本地曲库添加/移除歌曲，一首歌可属于多个歌单。
- 保存歌曲添加顺序，从歌单首个可播放条目开始播放；从中间曲目开始等交互可另行讨论。
- 重启后保留数据；本地歌曲失效时有明确状态和跳过规则。

**验收例子：**

1. 建立“通勤”和“学习”，同一首歌加入两者。
2. 从“通勤”移除歌曲，“学习”仍保留该曲，本地文件仍在。
3. 按顺序添加歌曲后重开 APP，添加顺序不变；首轮不要求手动调整顺序。
4. 在顺序播放模式下开始播放歌单，后续曲目符合保存顺序。
5. 用测试文件模拟外部删除后，APP 不崩溃，并按约定提示或跳过。

**实现边界：** 新增独立的歌单及条目模型，复用已有列表和播放入口。不把所有歌单挤入一个 favorites；首版不做账号同步、在线歌单迁移或自动封面。

**主要难点：** 歌曲标识与重新扫描后的关联、重复加入规则、列表顺序与播放队列的关系。

**课程展示价值：** 可以清楚展示需求、持久化、列表交互、播放联动和边界处理；能形成完整的小功能。

### B2. 跨字段搜索与筛选

**当前差异：** Lists.processQueryForMusic 只在 displayName 与 title 中按显示模式选一个字段，没有同时匹配歌手和专辑。[R7]

**最小范围：** 全部歌曲页同时匹配歌名、文件名、歌手、专辑；处理空值、空查询和大小写；再选一个时长范围或年份范围作为配套。保持现有隐藏规则含义清晰。

**验收例子：**

- 输入某个歌手名，在全曲结果中出现该歌手的歌曲。
- 当前按文件名显示，也能通过曲名找到歌曲。
- 某首歌缺少 title/artist，仍可通过其他有效字段检索且不崩溃。
- 清空查询后恢复预期列表；叠加筛选条件后结果正确。

**主要难点：** 查询规则一致、空字段处理、已有列表入口复用。此项通常比增加新的播放模式更少触及核心状态。

**定位：** 最适合第一项小交付；可以成为标签和未来自然语言检索的底座。

### B3. 最近播放与轻量历史

**用户问题：** 想找回“昨天听到的那首歌”，目前只有最后一首恢复状态。

**首版只做：** 最近播放页面、曲目和最后播放时间、重新播放、清空、重启保留。先明确“最近播放”是去重后的最近曲目，还是每次播放的时间线。

**后续再做：** 有效播放次数、常听排行、累计实际收听时长。后两者需要额外规则，不能由“点过播放按钮”直接推导。

**验收例子：**

- 后台自动切歌和通知栏切歌也能记录。
- 同一首暂停再恢复、页面重建不会反复增加历史事件或次数。
- 播放失败不写成成功听过。
- 清空历史同步更新存储与页面，不影响收藏或歌单。

**主要难点：** 事件记录应靠近播放器/服务生命周期；只在 Activity 点击列表时记数会漏掉后台行为。不要每秒重写整段 JSON 历史，也不要让历史无限增长。

若增加次数，先由团队明确一次会话、有效播放门槛和快速跳过规则；门槛是产品决定，并非固定行业标准。

### B4. 手动场景标签与筛选

**用户问题：** 歌手、专辑、文件夹无法表达个人的“学习、跑步、放松、睡前”等分类。

**最小范围：**

- 用户为歌曲新增、编辑、删除标签。
- 一首歌多个标签，一个标签对应多首歌。
- 按标签筛选，明确多标签是“满足任一”还是“满足全部”。
- 对结果播放或加入歌单；重启后保留。

**验收例子：** 标记几首“学习”，筛出相应歌曲；移除一个标签后结果立即更新；重启后关系正确；空结果有明确提示；同名歌曲不会误关联。

**实现边界：** 标签保存在 APP 内的用户元数据，不写回 MP3/ID3 文件；不把现有“隐藏某艺人/文件夹”重复包装成标签功能。

**与 AI 的关系：** 先让人能明确表达和修改标签，未来 AI 才能基于明确的数据提出筛选条件或标签建议。不把歌名当成判断实际音色情绪的充分依据。

### B5. 本地歌词

**用户问题：** 边听边看歌词、理解外语或练唱。

**两步交付：**

1. 手动给歌曲关联本地 TXT，在播放页查看。
2. 支持简单 LRC 时间戳，跟随播放位置高亮；之后再考虑偏移调整。

**验收例子：** 无歌词和坏文件不崩溃；关联重启保留；切歌不会显示上一首歌词；LRC 版在暂停、拖动进度、倍速时仍匹配当前播放位置。

**主要难点：** 文件选择与持久访问、编码、时间戳解析、歌词与歌曲匹配。首版不同时承诺联网搜词或自动生成歌词。

### B6. A–B 复读

**用户问题：** 整首重复不能方便地练习某一个句子或旋律。

**最小范围：** 设置 A、B，显示区间，到 B 返回 A；取消；切歌清除。

**验收例子：** 0 ≤ A < B ≤ duration；未设置 B 不启动循环；暂停恢复行为一致；与整曲重复、用户拖动和下一首操作的关系明确。

**主要难点：** 现有播放进度回调约每秒一次，不能直接把它当成精确的短片段边界检测器；要考虑 seek 完成和重复触发。[R11]

该功能能独立展示，但与播放核心耦合高于搜索和标签。它是区间循环的新增，不是重新实现已有的时间点收藏。

## 7. 推荐的推进组合

### 组合 A：围绕个人音乐库，优先建议

- 小交付：B2 跨字段搜索。
- 主功能：B1 多歌单。
- 根据 AI 方向选择配套：B4 标签，或 B3 最近播放。

这一组合可以演示“找到歌曲 → 整理成歌单 → 按自己的场景使用”。若时间有限，先完成 B1，加一个配套即可。

### 组合 B：围绕理解和练习音乐

- B5 本地歌词。
- 现有时间点收藏的命名/备注增强。
- B6 A–B 复读作为后续。

这一组合适合以后讨论歌词理解、练唱、语言学习。播放状态测试工作会更多。

### 首轮暂缓的范围

完整在线音乐平台、账号与云同步、大规模协同过滤、自动扫描整个音频库进行复杂分析，以及“整个播放器重写为另一套技术栈”，都不是完成上述基础增量的必要条件。等核心用户场景选定后再决定是否值得投入。

## 8. 开发前共同约定的少量事项

1. **歌曲身份与失效处理。** MediaStore ID 不能视为跨扫描永久不变；当前代码已尝试重新关联收藏与队列。[R3] 新歌单、历史、标签应共用一套曲目引用规则，不以歌名唯一。
2. **用户数据与扫描数据分开。** 扫描提供曲名、专辑等；用户编辑的歌单、标签和历史单独存储，避免刷新曲库时丢失。
3. **存储选择按范围决定。** 小数据可先封装当前保存方法；需要增长型历史/关系查询时可独立引入 Room。无需为选题先迁移所有旧设置。
4. **测试围绕行为。** 选择确定性样例文件，检查重启、删除音频、空字段、后台播放等与功能相关的场景；不把按钮能点击当成完整验收。
5. **贡献范围可追踪。** 保留上游来源，把已存在能力和团队新增内容分开描述；以本仓库功能分支、PR 和实际验收记录呈现工作。

额外代码细节供后续实现者注意：Music.dateAdded 当前取的是 MediaStore.DATE_MODIFIED；若实现“最近添加”规则，需先修正或明确它的时间语义，不能直接称作首次入库时间。[R3]

## 9. 下一轮 AI 讨论只需先明确方向

| 希望 AI 帮用户做的事 | 最有用的基础 |
| --- | --- |
| “帮我挑适合现在听的歌” | 多歌单、标签、搜索条件 |
| “更了解我的听歌偏好” | 最近播放、可信的播放事件、明确反馈 |
| “帮我理解或练习正在听的内容” | 歌词、书签管理、A–B 复读 |

当前应用播放的是本地曲库。未来 AI 生成结果应能对应到实际存在的歌曲，并可让用户预览、修改、保存和播放；缺少所需歌曲时应明确反馈。是否联网、使用哪种模型、提交哪些数据，等选定 AI 功能后再细化。当前没有选择模型、API 或新增服务。

## 10. AI 辅助与验证记录

ChatGPT 辅助完成静态源码核查、公开资料调研、候选比较和本稿起草。以上优先级与难度为设计建议；团队尚未确认最终选题。本次没有修改 APP 实现，没有执行 Android 构建、APK 运行或真机验证。
